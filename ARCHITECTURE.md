# Архитектура

## Общ преглед

Порталът е класическо клиент-сървър приложение:

- **Бекенд**: Node.js + Express + SQLite (`better-sqlite3`), обслужва REST
  API под `/api/*` и статичните файлове на публичния сайт и
  административния панел.
- **Фронтенд**: обикновени статични HTML/CSS/JS файлове в `public/`, без
  бъндлър и без фронтенд фреймуърк — плоски `<script>` тагове и глобални
  функции (`window.*`).
- **Данни**: единичен SQLite файл (`server/lom.db`), с базова схема
  (потребители, сесии, прикачени файлове) плюс схема, добавяна от всеки
  функционален модул.
- **Тестове**: `node:test` + `supertest` за бекенда, Playwright за
  end-to-end сценарии през реалния браузър.

## Ключово архитектурно решение: авто-зареждащ се регистър на модули

Проектът е проектиран така, че **пет функционални модула** (бюджет и
разходи, обществени поръчки, решения на Общинския съвет, наредби,
администрация) могат да бъдат разработвани **паралелно от отделни агенти**,
без нито един от тях да се налага да редактира споделените базови файлове,
изградени в тази основа (`server/db/index.js`, `server/routes/index.js`,
`server/server.js` и т.н.).

### Защо това е важно

Ако всеки модул трябваше да добавя своите таблици в `server/db/index.js`
или да регистрира маршрутите си в `server/routes/index.js`, пет паралелни
агента/разработчици биха редактирали **един и същи файл** едновременно —
което гарантирано води до конфликти при merge, дори при добронамерена и
коректна работа на всеки от тях. Вместо това всеки модул получава **своя
собствена директория**, в която добавя **само нови файлове**:

- `server/db/modules/*.js` — схема на модула (таблици, индекси)
- `server/routes/modules/*.js` — API маршрути на модула
- `server/scraper/modules/*.js` — (по избор) логика за извличане на данни
  от lom.bg за този модул

Базовите файлове само "сканират" тези директории при стартиране и зареждат
всичко, което открият — без да "знаят" предварително имената на модулите.
Така пет агента могат да работят едновременно, всеки добавяйки нов файл в
съответната `modules/` директория, без нито един diff да пресича файл,
докосван от друг агент.

### Как работи механизмът

**1. Схема на базата данни (`server/db/modules/*.js`)**

При стартиране `server/db/index.js`:

1. Създава базовите таблици (`users`, `sessions`, `attachments`).
2. Чете всички `.js` файлове в `server/db/modules/`, сортирани по азбучен
   ред (детерминиран, предвидим ред на зареждане).
3. За всеки файл извиква `require(...)`; ако експортираният обект има
   функция `defineSchema(db)`, тя се извиква с отворената `better-sqlite3`
   връзка.

Всеки модул дефинира собствените си таблици чрез `CREATE TABLE IF NOT
EXISTS ...` вътре в своя `defineSchema(db)`. Пример за скелет на файл,
който модулен агент би добавил в `server/db/modules/budget.js`:

```js
function defineSchema(db) {
  db.exec(`
    CREATE TABLE IF NOT EXISTS budget_lines (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      -- ... специфични за модула колони ...
      review_status TEXT NOT NULL DEFAULT 'pending',
      reviewed_by INTEGER,
      reviewed_at TEXT,
      created_at TEXT NOT NULL DEFAULT (datetime('now'))
    );
  `);
}

module.exports = { defineSchema };
```

**2. API маршрути (`server/routes/modules/*.js`)**

Аналогично, `server/routes/index.js`:

1. Монтира базовите маршрути (`/auth/*`, `/attachments/*`, `/review/*`).
2. Чете всички `.js` файлове в `server/routes/modules/`, сортирани по
   азбучен ред.
3. За всеки файл прави `router.use(require(...))` — файлът трябва да
   експортира `express.Router()`.

**3. Извличане на данни (`server/scraper/modules/*.js`)**

`server/scraper/runAll.js` (стартиран чрез `npm run sync`) зарежда и
изпълнява всеки модул в `server/scraper/modules/` по същия принцип — всеки
файл експортира `async function` по подразбиране (default export), която
извлича и записва данни. Грешка в един модул се логва, но не спира
останалите — важно е седмичният job да не се провали изцяло заради един
чупещ се източник.

### Регистър за преглед (`server/reviewRegistry.js`)

За да могат админ-панелът и `GET /api/review/pending` да показват "чакащи
одобрение" елементи от всички модули **генерично** (без да "познават"
имената на таблиците на всеки модул предварително), всеки модул регистрира
таблицата си при зареждане:

```js
const { registerReviewable } = require('../../reviewRegistry');

registerReviewable({
  key: 'budget',
  table: 'budget_lines',
  titleColumn: 'title',
});
```

`server/routes/review.js` използва този регистър, за да построи SQL заявки
динамично (`SELECT * FROM <table> WHERE review_status = 'pending'`).
Стойностите в регистъра се задават **само от доверен, hardcoded код на
модулите** — никога от потребителски вход — така изграждането на динамичен
SQL върху `table` е безопасно. Валидацията на `table` параметъра в
`POST /review/:table/:id/approve|reject` спрямо регистъра е реалната
защитна граница (403 при непознато име на таблица) — не просто предпазна
мярка срещу SQL injection, а контрол кои таблици изобщо могат да бъдат
модифицирани през този маршрут.

### Резултат

Пет агента могат едновременно да:

1. Добавят `server/db/modules/<their-module>.js`
2. Добавят `server/routes/modules/<their-module>.js`
3. (По избор) добавят `server/scraper/modules/<their-module>.js`
4. Добавят собствени страници в `public/<their-module>/` и
   `public/admin/<their-module>.html`

— без нито един от тях да докосва файл, докосван от друг модул, и без нужда
от координация кой пръв ще редактира споделен файл.

## Функционални модули

Кратко резюме на всеки от петте модула: какво покрива, откъде идват
реалните му данни и какви са честно установените ограничения на източника
(за да не се създава грешно впечатление за пълнота на данните).

### Бюджет и разходи (`budget`)

Проекти, бюджетни редове (разпределени средства по година/източник на
финансиране) и разходи (плащания по доставчици), плюс обобщено табло
(`GET /api/dashboard/budget`) с разпределено срещу изразходвано по
категория и по година.

**Реален източник**: `https://lom.bg/section-56-content.html` — хронологичен
списък от свързани с бюджета решения и отчети, **не** истински "проектен
регистър". На lom.bg няма публикуван разбит по проекти бюджет, затова
скрейперът честно групира свързаните документи по бюджетна година и създава
по един "проект" на година (напр. "Общински бюджет 2024") с прикачените към
нея документи. Скрейперът **не** измисля проектно-ниво финансова
детайлност, каквато не съществува в източника — конкретните разпределени/
изразходвани суми за такъв "проект" се въвеждат ръчно от администратор въз
основа на прикачените документи.

### Обществени поръчки (`procurement`)

Процедури по обществени поръчки с жизнен цикъл на статуса (обявена / в ход
/ възложена / приключена / прекратена), прогнозна стойност, изпълнител,
стойност и дата на договора, с незадължителна връзка към проект от модул
"Бюджет".

**Реален източник**: собствената страница "Профил на купувача" на lom.bg
не е използваема — съдържа само 3 контакта на служители и 3 изходящи
връзки. Националната платформа ЦАИС ЕОП (`app.eop.bg`) е Angular SPA без
сървърно рендиран HTML и без публично достъпен API, извлечим с обикновена
заявка — извън обхвата на този лек скрейпър (би изисквал headless
браузър). Вместо това модулът извлича данни от `e-obp.eu/bp/Lom` — реален,
сървърно рендиран ASP.NET сайт с действителен, филтрируем списък от
процедурите на Община Лом (стотици записи, 2014–2026), покриващ всичките 5
типа листинг на този сайт. **Честно ограничение**: от страниците с
листинги надеждно се извличат само `title`, `procedure_type`,
`publish_date` и `source_url` — `estimated_value`, `deadline_date`,
статус отвъд подразбиращия се `'обявена'`, `awarded_contractor`,
`contract_value` и `contract_date` **не** се попълват автоматично и трябва
да бъдат въведени ръчно от администратор при преглед.

### Решения на Общинския съвет (`decisions`)

Решения на Общинския съвет по сесии, с прикачени PDF материали.

**Реален източник**: `lom.bg/section-263-content.html` (списък) плюс
страниците за детайли на всяка сесия. **Честно ограничение**: прикачените
PDF файлове на практика са сканирани предварителни материали за дневния
ред (не протоколи след заседанието), заради което `pdf-parse` често връща
празен текст от тях — номерата на решенията често не могат да бъдат
извлечени автоматично по тази причина, идваща от самия източник, не от
грешка в парсера, и се оставят с плейсхолдър текст до ръчен преглед.

### Наредби (`ordinances`)

Наредби на общината със статус (действаща/отменена) и категория.

**Реален източник**: `lom.bg/subsection-34-naredbi.html` — плосък,
неструктуриран списък от `<p>` параграфи, без дати и без статус никъде в
източника. **Честно ограничение**: `adoption_date` умишлено се оставя
`NULL`, вместо да се познава/грешно извлича; статусът по подразбиране е
`'active'` до ръчна корекция от администратор.

### Администрация (`administration`)

Отдели, служители, общински съветници (мандат 2023–2027) и постоянни
комисии с членския им състав.

**Реален източник**: `lom.bg/section-52-kontakti.html` за общи контакти —
**слаб** източник: само 2 общи контактни блока (общинска администрация и
Общински съвет), а страницата изрично посочва, че телефонният указател на
служителите е "в процес на актуализация" — на нея **няма** реален регистър
по отдели/служители и модулът съзнателно не си измисля такъв. Реалните
структурирани регистри идват от други страници: `subsection-35`
(общински съветници по партии за текущия мандат) и `subsection-36`
(постоянни комисии и техният състав) — за тях данните са пълни за текущия
мандат.

## Автентикация и сесии

- Единствен администраторски акаунт, засят при първо стартиране
  (`server/db/index.js`).
- Сесиите се пазят в таблица `sessions` (не JWT) — токен от 32 случайни
  байта (`crypto.randomBytes`), поставен в `httpOnly` бисквитка `lt_sid`.
- `requireAuth` / `requireAdmin` (в момента еквивалентни — виж SECURITY.md)
  защитават администраторските маршрути.

## Начална страница и връзки между модулите

`public/index.html` е реалната начална страница на портала: кратко въведение
плюс секция "Порталът в момента", която на клиента извиква
`GET /api/dashboard/budget`, `GET /api/projects`, `GET /api/procurements`,
`GET /api/council-decisions` и `GET /api/ordinances?status=active`
паралелно през `fetchJson`. Всяка от тези пет извиквания има собствен
`try/catch` — временна недостъпност на един модул (напр. рестартиране,
грешка в БД) показва плочка "временно недостъпно" само за него, без да
чупи останалата част от страницата.

Модулите "Бюджет" и "Обществени поръчки" са кръстосано свързани чрез
незадължителната колона `procurement.project_id`:

- `GET /api/procurements/:id` връща и `project: { id, name } | null` —
  името и връзката към `/budget/project.html?id=<id>`, само ако свързаният
  проект също е одобрен за публикуване.
- `GET /api/projects/:id` връща и `procurements: [...]` — одобрените
  поръчки, свързани с проекта, с връзка към
  `/procurement/detail.html?id=<id>`.
- `GET /api/procurements` поддържа и `?project_id=` филтър за същата цел.

## Прикачени файлове

Универсална таблица `attachments`, свързана полиморфно чрез
(`entity_type`, `entity_id`) към записи от кой да е модул (проект, разход,
бюджетен ред, поръчка, решение на ОбС, наредба, служител). Позволява
единна логика за качване/изтегляне/изтриване на файлове, преизползваема от
всички модули, без дублиране на код или собствени `uploads` таблици на
модул.
